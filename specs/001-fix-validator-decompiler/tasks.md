# Tasks: Устранение дефектов валидатора и декомпилятора

**Input**: Design documents from `/specs/001-fix-validator-decompiler/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/cli.md, quickstart.md

**Tests**: обязательны. Половина требований (FR-006…FR-011) — про проверки как
таковые, а остальные дефекты обнаружены именно отсутствием проверок. Тест пишется
раньше исправления и обязан упасть на текущем коде: падение — доказательство, что
дефект воспроизведён, а не додуман.

**Organization**: задачи сгруппированы по историям спецификации. Порядок фаз
следует приоритетам, кроме перечня моделей: он вынесен в фазу 2, потому что от
него зависят проверки трёх историй.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: можно делать параллельно (разные файлы, нет незакрытых зависимостей)
- **[Story]**: к какой истории относится задача
- Пути указаны от корня репозитория

## Path Conventions

Проект — модуль Go в `ramusc/`. Исходники — `ramusc/internal/…` и
`ramusc/cmd/ramusc`, тесты лежат рядом с кодом (`*_test.go`), данные проверок —
`ramusc/testdata/`. Отдельного каталога `tests/` в проекте нет и не заводится.

## Dependencies & Execution Order

### Phase Dependencies

- **Phase 1 (Setup)**: без зависимостей
- **Phase 2 (Foundational)**: после Setup; блокирует истории 1, 2 и 4
- **Phase 3 (US1, P1)**: после Phase 2
- **Phase 4 (US2, P1)**: после Phase 3 — проверка «вывод принимается языком» имеет смысл только когда отказ уже отделяет модели, для которых вывода не будет
- **Phase 5 (US3, P2)**: после Phase 2; от историй 1 и 2 не зависит, может идти параллельно с ними
- **Phase 6 (US4, P3)**: после Phase 2; T036 удобнее делать после Phase 4
- **Phase 7 (US5, P4)**: после всех предыдущих — описывает установленные ими границы
- **Phase 8**: последняя

### Порядок внутри историй

- Тест пишется раньше исправления и обязан упасть на текущем коде
- В US1: обнаружение классификаторов (T008) → колонки (T009) → строки и значения (T010); проход обнаружения (T011) → подключение к команде (T012); перенос в IR (T013) → печать (T014) → снятие мёртвой проверки (T015)
- В US2: адресация (T019, T020) → снятие повторов (T021) → сверка эталонов (T022)

### Единственная зависимость между историями

US2 зависит от US1 (задача T012): пока отказ не отделяет `testModel.rsf`, проверка

## Implementation Strategy

### MVP (только User Story 1)

1. Phase 1 — базовая линия воспроизводится
2. Phase 2 — перечень моделей
3. Phase 3 — классификаторы и отказ
4. **Остановиться и проверить**: `decompile testdata/testModel.rsf` даёт код 2 с
   перечнем находок; проверка разбора находит пять справочников
5. Это уже самостоятельная ценность: худший из дефектов — молчаливая потеря —
   устранён, даже если остальное не сделано

### Инкрементальная поставка

1. Phase 1–2 → основание
2. + US1 → молчаливой потери нет (MVP)
3. + US2 → вывод не искажает модель и принимается языком
4. + US3 → все сообщения проверены
5. + US4 → обе модели в проверках
6. + US5 → описание соответствует коду

Каждый шаг добавляет ценность и не ломает предыдущие.
