# Модель данных: покрытие, схлопывание, явный туннель

Новых сущностей в IR почти нет: одно поле у работы. Меняется не форма данных, а
то, по какому ключу они сопоставляются.

## 1. Три ключа, вокруг которых вся фича

Все три дефекта — это один и тот же вопрос «что с чем считать одним и тем же»,
заданный в трёх местах.

| Ключ | Где живёт | Из чего состоит | Что решает |
|---|---|---|---|
| **Ключ оверрайда** | `layout.placeArrows` | поток + диаграмма | какие стрелки раскладка не трогает |
| **Ключ связи** | `layout.diagramArrows`, `validate` | диаграмма + поток + производитель + потребитель + сторона потребителя | что считать одной и той же связью |
| **Ключ узла** | `rsf`, правило туннелей | номер кросспоинта | что считать одной точкой |

Ключ связи — единственный, который нужен в двух пакетах сразу: `layout` им
схлопывает, `validate` им же находит дубль и проверяет покрытие. Считается он в
обоих местах одинаково и по одним и тем же полям IR; общего типа под него не
заводится — пакеты не должны знать друг о друге больше необходимого (принцип IV).

## 2. Что меняется в языке: `tunnel` у работы

```yaml
- name: Приём заказа
  kind: dfd
  in:        [Заявка]
  control:   [Регламент приёма]
  mechanism: [Менеджер]
  out:       [Заявка в работе]
  tunnel:    [Регламент приёма, Менеджер]
```

| Поле | Тип | Смысл |
|---|---|---|
| `tunnel` | список имён потоков (`flowList`) | потоки, которые намеренно не переходят в декомпозицию этой работы |

Список, а не флаг у каждой стороны: туннелируется **стрелка**, а не сторона, и
один и тот же поток не приходит к работе двумя сторонами — об этом уже говорит
`flow_side_mismatch`.

Поле необязательное; отсутствие равносильно пустому списку. Поток, названный в
`tunnel`, обязан быть среди `in`/`control`/`mechanism`/`out` той же работы —
иначе туннелировать нечего.

### Соотношение с уже существующим `tunnel`

В языке уже есть `tunnel: true` — у **конца сегмента** в `layout.arrows`
(`ir.Endpoint.Tunnel`, `$defs/endpoint`). Это разные вещи и они не сливаются:

| | `functions[].tunnel` | `layout.arrows[].segments[].from/to.tunnel` |
|---|---|---|
| О чём | о модели: стрелка не идёт вглубь | о рисунке: этот конец в скобках |
| Кто пишет | автор, осмысленно | декомпилятор, перенося чужой файл |
| Обязателен | нет | нет |

Новое поле — утверждение о модели, старое — часть геометрии. Первое проверяется
валидатором, второе доезжает до файла как есть.

## 3. Что меняется в IR

```go
// ir.Function
type Function struct {
    Name Ref
    Of   Ref
    Kind Ref
    Type Ref
    Note string
    Raw  []RawAttr

    Tunnel []Ref // новое: потоки, не переходящие в декомпозицию
    ...
}
```

Одно поле, один разбор в `ir.Build`, одна обратная запись в `decompile`.
`ir.Link`, `ir.Segment` и `ir.Endpoint` не меняются вовсе: ключи из §1
складываются из полей, которые там уже есть (`Link.Flow`, `Link.From`,
`Link.To`, `Link.SideName()`, `Segment.On`, `Segment.Context`).

`Link.Sugar` — поле, которое до сих пор влияло только на тексты сообщений, —
начинает работать: дублем считается пара, где одну половину дал ICOM
(`Sugar == true`), а другую — явная запись `links` (`Sugar == false`).

## 4. Покрытие связи сегментом

Понятие, которое появляется в `validate` ради `incomplete_arrow_layout`.

Сегмент из `layout.arrows` **покрывает** связь, если совпали диаграмма, поток и
тот конец связи, который назван в сегменте блоком:

| Связь | Покрывающий сегмент |
|---|---|
| поток к работе стороной `S` | сегмент этой стрелки на той же диаграмме, у которого `to` = эта работа со стороной `S` |
| поток от работы наружу | сегмент, у которого `from` = эта работа со стороной `out` |

Сегменты, оба конца которых — край листа или узел (магистраль, перегоны между
узлами), не покрывают ничего и проверке не мешают: они обслуживают дерево, а не
связь.

Отсюда правило: **если у потока на диаграмме есть хоть один авторский сегмент,
то каждая связь этого потока на этой диаграмме обязана быть покрыта.** Непокрытая
даёт `incomplete_arrow_layout`.

## 5. Наполнение кросспоинта

Понятие, которое появляется в `internal/rsf` ради правила туннелей. Считается по
таблице `attribute_sector_borders` уже собранного файла.

| Часть | Откуда |
|---|---|
| `outs` узла | секторы, у которых **начало** (`F_SECTOR_BORDER_START`) несёт этот номер |
| `ins` узла | секторы, у которых **конец** (`F_SECTOR_BORDER_END`) несёт этот номер |

Конец сектора рисуется в скобках, когда у его узла пуст `ins` либо пуст `outs`,
**кроме** двух случаев:

1. конец на краю листа контекстной диаграммы A-0;
2. конец, прицепленный к блоку без декомпозиции.

Полное правило и его происхождение — `research.md`, В1; исполняемая запись —
`evidence/tunnels.py`.

## 6. Состояния, которых нет

Ни одна часть фичи не заводит состояния и переходов. Всё вычисляется за один
проход по документу или по файлу, повторный запуск на том же входе даёт тот же
результат — этого требует принцип III.
