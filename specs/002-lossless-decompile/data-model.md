# Phase 1. Модель данных

Описываются только новые сущности и изменяемые. Остальное в IR и `internal/rsf`
остаётся как есть.

## Опись атрибутов элемента

Новая сущность в `internal/rsf`. Отвечает на вопрос «что вообще лежит в файле про
этот элемент» — независимо от того, что мы умеем читать.

### `rsf.Attribute`

| Поле | Источник | Примечание |
|---|---|---|
| `ID` | `attributes.ATTRIBUTE_ID` | |
| `Name` | `attributes.ATTRIBUTE_NAME` | напр. `F_STATUS` |
| `Table` | имя таблицы значений | напр. `attribute_statuses` |
| `Element` | элемент-владелец | |
| `Columns` | колонка → значение | без ключей записи |

**Ключи записи** (`ATTRIBUTE_ID`, `ELEMENT_ID`, `ELEMENT1_ID`,
`VALUE_BRANCH_ID`, `REMOVED_BRANCH_ID`) в `Columns` не входят: это адрес значения,
а не само значение. Иначе люк заполнится служебными числами, и читать его станет
невозможно.

**Порядок.** Атрибуты одного элемента — по возрастанию `ATTRIBUTE_ID`; колонки
внутри атрибута — в порядке объявления в таблице. Детерминированность вывода
(принцип III) требует явного порядка в обоих местах.

**Отбор.** Значения берутся из всех таблиц `attribute_*`, где есть колонка
`ELEMENT_ID` или `ELEMENT1_ID`. Таблицы без такой колонки описывают не элемент, а
сам атрибут (`attribute_other_element_properties`,
`attribute_element_list_properties`) — в опись не входят и используются отдельно
для цели ссылочной колонки.

## Переносимые виды элементов

Закрытый список из пяти видов (Р-2). Всё, что не принадлежит ни одному из них, —
метамодель, и в опись не попадает.

| Вид | Как опознаётся |
|---|---|
| работа | элемент квалификатора работ модели |
| поток | элемент квалификатора `F_STREAMS` |
| сектор | элемент квалификатора `F_SECTORS` |
| строка справочника | элемент пользовательского классификатора |
| модель | элемент `F_BASE_FUNCTIONS`, найденный `findModel` |

**Почему список положительный.** Открыто множество атрибутов — там и живёт
незнакомое, там нужен чёрный список. Множество видов элементов закрыто и мало;
шестой вид добавляется осознанно.

## Потеря

Заменяет собой нынешний перечень `Unsupported`, построенный белым списком.

### `rsf.Loss`

| Поле | Смысл |
|---|---|
| `Attribute` | имя атрибута Ramus |
| `Kind` | вид элемента-владельца |
| `Columns` | какие именно колонки не перенесены |
| `Count` | на скольких элементах встретилось |

**Как вычисляется.** Опись минус перенесённое. «Перенесённым» атрибут считается
**по колонкам** (Р-4): запись о модели, из которой прочитаны две колонки из
девяти, даёт потерю по остальным семи, а не считается перенесённой целиком.

**Свёртка.** Одна и та же потеря на сотне элементов — одна запись с количеством
(FR-005). Перечень из ста одинаковых строк никто читать не станет.

**Отношение к отказу.** `Unsupported` из фичи `001` никуда не девается: он про
содержимое, которое языком не выражается по существу (работа без имени), и
по-прежнему ведёт к отказу. `Loss` — про перенесённую модель, лишившуюся части
оформления, и ведёт к предупреждению. Две сущности, два канала, не смешивать.

## Запись люка

### `ir.RawAttr` (существует, не меняется)

| Поле | Смысл |
|---|---|
| `Attribute` | имя атрибута Ramus, напр. `F_STATUS` |
| `Value` | значение как есть |

**Форма значения** (Р-5):

| Атрибут | Значение |
|---|---|
| одноколоночный (`attribute_texts`, `_longs`, `_colors`) | скаляр |
| многоколоночный (`F_SECTOR_PROPERTIES`, `F_PROJECT_PREFERENCES`) | отображение «колонка → значение» |

Значение не разбирается и не проверяется: смысл люка в том, чтобы не упираться в
потолок формата (Р9).

**Порядок записей** — по имени атрибута. Порядок обхода отображения в Go не
определён, а вывод обязан быть детерминированным.

## Где появляется люк

Изменение входного языка (FR-016), фиксируется решением в `DESIGN-DECISIONS.md`.

| Элемент языка | Люк был | Станет | Что ляжет сегодня |
|---|---|---|---|
| работа | да | да | цвета, шрифт, статус, тип декомпозиции, даты |
| поток | да | да | ничего |
| строка справочника | да | да | ничего |
| **модель (верхний уровень)** | нет | да | непрочитанные колонки записи о модели, статус, даты |
| **сегмент стрелки** | нет | да | свойства подписи, альтернативная подпись |
| **классификатор** | нет | да | ничего |
| **колонка** | нет | да | ничего |

**Необязательность.** Люк во всех новых местах необязателен. Документ,
написанный человеком и не содержащий ни одного люка, остаётся валидным — иначе
расширение сломало бы все существующие модели.

**Куда именно у стрелки.** Атрибуты принадлежат сектору, а сектор в языке — это
сегмент (`layout.arrows[].segments[]`). Люк ставится сегменту, а не стрелке
целиком: у разных сегментов одной стрелки свойства подписи разные.

## Цель ссылочной колонки

### Изменение `ir.Column.Of`

Поле существует в языке и в IR, но декомпилятором не заполняется.

| Тип колонки | Где лежит цель |
|---|---|
| `Core.OtherElement` → `ref` | `attribute_other_element_properties.QUALIFIER` |
| `Core.ElementList` → `list` | `attribute_element_list_properties.QUALIFIER1` / `QUALIFIER2` |

Найденный идентификатор квалификатора переводится в имя справочника: язык
адресует по именам (Р4).

**Печатается только у ссылочных колонок.** У колонки типа `text` поля цели быть
не должно — валидатор считает это ошибкой (`unexpected_column_target`).

**Невыясненное.** Какая из `QUALIFIER1`/`QUALIFIER2` означает цель — по имеющимся
файлам не определить (Р-8). Решается при реализации на собранных вручную данных.

## Что не меняется

- Побайтовый round-trip: он про слой таблиц, а перенос в язык его не касается.
- Отказ по `Unsupported` и его три вида.
- Коды диагностики: перечень потерь не проходит через `internal/diag`.
- Элементы DFD: сняты с объёма решением по фиче `001`.
