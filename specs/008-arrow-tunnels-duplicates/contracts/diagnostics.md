# Контракт: диагностика

Три новых кода. Существующие не переименовываются и смысла не меняют — коды
только добавляются (принцип II).

> Третий код, `flow_escapes_diagram`, добавлен при реализации: FR-009 требует
> назвать случай «поток уходит за край дочерней диаграммы, а у родителя такой
> стороны нет», и подходящего кода не нашлось. Именно он давал пятый туннель
> в `skirt-full.yaml`.

## 1. `incomplete_arrow_layout`

| Поле | Значение |
|---|---|
| `severity` | `error` |
| `code` | `incomplete_arrow_layout` |
| `path` / `line` / `column` | позиция стрелки в `layout.arrows` — той, чьи сегменты не покрыли связь |

**Когда**: у потока на диаграмме есть хоть один авторский сегмент, но какая-то
связь этого потока на этой же диаграмме не покрыта ни одним из них
(определение покрытия — `data-model.md`, §4).

**Почему ошибка, а не предупреждение**: непокрытая связь просто не попадает в
файл. Это та же молчаливая потеря, от которой заводится фича, только этажом
ниже.

**Текст**:

```
на диаграмме «Изготовление юбки» сегменты потока «Правила изготовления»
не доходят до работы «Добавление фурнитуры»: взявшись рисовать поток
на диаграмме, опишите все его связи там
```

Для связи, уходящей наружу, — та же форма со словом «из»:

```
на диаграмме «Изготовление юбки» сегменты потока «Юбка» не выходят
из работы «Добавление фурнитуры»: ...
```

## 2. `duplicate_link`

| Поле | Значение |
|---|---|
| `severity` | `warning` |
| `code` | `duplicate_link` |
| `path` / `line` / `column` | позиция записи в `links` — той, что повторяет уже выраженное списками ICOM |

**Когда**: связь выражена дважды — половинками ICOM (`out` у производителя плюс
`in`/`control`/`mechanism` у потребителя) и явной записью `links` с теми же
потоком, концами и стороной потребителя.

**Почему предупреждение**: FR-005 требует, чтобы в файле оказался ровно один
сектор. При `error` файла не будет вовсе, и требование стало бы невыполнимым.
Это единственная диагностика фичи, где severity выбрана, а не продиктована
(`research.md`, В6).

**Текст**:

```
связь «Заготовка» из «Первая» в «Вторая» стороной in уже выражена
списками in/out этих работ: запись в links ничего не добавляет,
в файл поедет одна стрелка
```

**Не срабатывает**, когда стороны потребителя различаются: ICOM говорит `in`, а
`links` — `control`. Это две разные стрелки, и схлопывать их нельзя (FR-007).

## 3. Что делает компилятор помимо сообщения

| Код | Компиляция | Что в файле |
|---|---|---|
| `incomplete_arrow_layout` | останавливается, код возврата 1 | файла нет |
| `flow_escapes_diagram` | останавливается, код возврата 1 | файла нет |
| `duplicate_link` | продолжается, код возврата 0 | один сектор на связь |

Схлопывание дубля идёт **до** раздачи мест на сторонах блока: иначе сторона
делится на `n+1` частей при завышенном `n`, и единственная стрелка садится не в
середину. В воспроизведении это видно — вход «Второй» поделён на три части
вместо двух.

## 3а. `flow_escapes_diagram`

| Поле | Значение |
|---|---|
| `severity` | `error` |
| `code` | `flow_escapes_diagram` |
| `path` / `line` / `column` | позиция потока в `out` работы-производителя |

**Когда**: поток произведён на диаграмме, никто на ней его не потребляет — то
есть стрелка уходит за край листа, — а у работы, которой диаграмма принадлежит,
такого выхода нет. Конец на краю остаётся без пары на родительской диаграмме, и
Ramus рисует его в скобках.

**Почему это отдельный код, а не `flow_not_produced`**: тот идёт от потребителя
(«поток потребляют, а никто не выдаёт»). Здесь зеркальный случай, и половина
баланса со стороны производителя до сих пор не проверялась вовсе.

**Снимается** объявлением потока в `out` работы-владельца диаграммы либо в её
`tunnel`.

**Текст**:

```
поток «Отход» выходит из работы «Обработка», на диаграмме работы
«Производство» его никто не потребляет, и у работы «Производство»
такого выхода нет: стрелка уйдёт за край листа и оборвётся.
Добавьте поток в out работы «Производство» либо назовите его в её tunnel
```

## 4. Существующий `flow_not_decomposed` расширяет охват

Код, текст и severity не меняются. Меняется множество случаев, на которых он
возникает: `checkDecomposition` перестаёт пропускать работы с `kind: dfd`.

| | Было | Стало |
|---|---|---|
| ICOM работы IDEF0 не дошёл до декомпозиции | `flow_not_decomposed` | без изменений |
| ICOM работы DFD не дошёл до декомпозиции | молчание, туннель в файле | `flow_not_decomposed` |
| То же, но поток назван в `tunnel` работы | — | молчание, туннель в файле — намеренный |

Это не переименование и не смена смысла кода: сообщение по-прежнему говорит
«поток приходит к работе, но в её декомпозиции его никто не принимает». GUI,
ветвящийся по коду, менять не придётся.

## 5. Покрытие видами диагностики

`internal/diag/coverage_test.go` требует, чтобы каждый код возникал хотя бы на
одной модели из `testdata/models/`. Новые коды приносят свои модели:

| Код | Модель |
|---|---|
| `incomplete_arrow_layout` | `testdata/models/partial-arrow-layout.yaml` |
| `duplicate_link` | `testdata/models/duplicate-link.yaml` |
| `flow_escapes_diagram` | `testdata/models/flow-escapes.yaml` |
| `flow_not_decomposed` на DFD | `testdata/models/dfd-no-tunnel.yaml` |

`duplicate-link.yaml` — единственная модель каталога, дающая одно лишь
предупреждение. `TestGolden` пришлось поэтому смягчить с «хотя бы одна ошибка»
до «хотя бы одна диагностика»: вид, который по смыслу может быть только
предупреждением, иначе не проверить, а `coverage_test` читает этот же каталог.
Настоящая защита осталась — модель, не давшая ничего, роняет сборку.

Эталоны — `testdata/golden/<имя>.diag.json`, переписываются `make golden`.
