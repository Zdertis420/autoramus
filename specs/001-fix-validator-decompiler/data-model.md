# Phase 1. Модель данных

Описываются только сущности, которых сегодня нет или которые меняются. Всё
остальное в IR и `internal/rsf` остаётся как есть.

## Классификатор

Появляется в `internal/rsf` как понятие формата и переносится в уже существующий
`ir.Classifier`, который входной язык и валидатор поддерживают с самого начала.

### `rsf.Classifier`

| Поле | Источник в `.rsf` | Примечание |
|---|---|---|
| `ID` | `qualifiers.QUALIFIER_ID` | идентичность, не имя |
| `Name` | `qualifiers.QUALIFIER_NAME` | имя справочника |
| `NameAttribute` | `qualifiers.ATTRIBUTE_FOR_NAME` | колонка, играющая роль имени строки |
| `Columns` | см. ниже | без системных |
| `Rows` | см. ниже | может быть пустым |

**Правило отбора.** Классификатор — квалификатор, у которого
`QUALIFIER_SYSTEM = FALSE` и `QUALIFIER_ID` не равен квалификатору работ модели
(тот находится через `F_BASE_FUNCTION_QUALIFIER_ID`). Отбор по признаку, не по
имени: имена пользовательские и ни о чём не говорят.

**Порядок.** По возрастанию `QUALIFIER_ID`. Детерминированность вывода (принцип III)
требует явного порядка; идентификатор возрастает в порядке создания справочников
автором, что совпадает с ожидаемым.

### `rsf.Column`

| Поле | Источник | Примечание |
|---|---|---|
| `ID` | `attributes.ATTRIBUTE_ID` | |
| `Name` | `attributes.ATTRIBUTE_NAME` | |
| `Type` | `ATTRIBUTE_TYPE_PLUGIN_NAME` + `.` + `ATTRIBUTE_TYPE_NAME` | напр. `Core.Text` |
| `Position` | `qualifiers_attributes.ATTRIBUTE_POSITION` | порядок колонок |

**Правило отбора.** Колонки берутся из `qualifiers_attributes` по `QUALIFIER_ID`;
записи с `attributes.ATTRIBUTE_SYSTEM = TRUE` отбрасываются — их выдаёт сам Ramus,
автор их не создавал. Проверено: у пустого справочника остаются две колонки,
`HierarchicalAttribute` (системная, отбрасывается) и `Name` (не системная,
переносится).

**Порядок.** По `ATTRIBUTE_POSITION`, при равенстве — по `ATTRIBUTE_ID`. В
`testModel.rsf` позиция у обеих колонок нулевая, поэтому вторичный ключ обязателен,
иначе порядок будет зависеть от обхода таблицы.

### `rsf.Row`

| Поле | Источник | Примечание |
|---|---|---|
| `ID` | `elements.ELEMENT_ID` | |
| `Values` | `attribute_<тип>` по паре (`ELEMENT_ID`, `ATTRIBUTE_ID`) | отсутствие записи ≠ пустая строка |

**Правило отбора.** Строки — элементы с этим `QUALIFIER_ID`. Порядок — по
`ELEMENT_ID`.

**Соответствие типов колонки и таблицы значений:**

| Тип колонки | Таблица значений |
|---|---|
| `Core.Text` | `attribute_texts` |
| `Core.Long` | `attribute_longs` |
| `Core.Double` | `attribute_doubles` |
| `Core.Date` | `attribute_dates` |
| `Core.Boolean` | `attribute_booleans` |
| `Core.ElementList` | `attribute_element_lists` — ссылка на строки |

Тип, которого нет в таблице соответствия, — непереносимое содержимое (см. ниже).

### Перевод в `ir.Classifier`

Существующая структура IR не меняется. Соответствие прямое: имя → имя, колонка →
колонка с типом входного языка, строка → строка со значениями по именам колонок.
Ссылка `Core.ElementList` переводится в ссылку на строку, а не в её значение
(требование edge case из спецификации).

## Непереносимое содержимое

Новая сущность. Собирается проходом по таблицам `.rsf` **до** начала печати.

### `rsf.Unsupported`

| Поле | Смысл |
|---|---|
| `Kind` | вид: безымянная работа, неизвестный тип колонки, … |
| `Count` | сколько таких находок |
| `Where` | к какому элементу относится, если применимо |

**Виды, известные на сегодня:**

| Вид | Как обнаруживается | Почему непереносимо |
|---|---|---|
| работа без имени | элемент квалификатора работ без значения атрибута имени | Р4: имя — идентификатор, пустых быть не может |
| тип колонки без соответствия | `ATTRIBUTE_TYPE_*` вне таблицы выше | значение нечем выразить |
| работа с именем-дублем | два элемента квалификатора работ с одинаковым нормализованным именем | Р4 требует уникальности |

Список открыт: при появлении новой находки добавляется вид, а не новая ветка в
печати.

**Инвариант.** Проход не опирается на результат разбора. Он смотрит в таблицы и
верен даже там, где разбор чего-то не умеет, — это и есть требование FR-002.

**Полнота.** Проход собирает все находки и не прекращается на первой: FR-004
требует сообщить автору обо всех сразу.

## Изменение адресации работ

Сегодня `internal/decompile` строит отображение работ по нормализованному имени
(`sides[f.Name.Name]`). Имена в `.rsf` не уникальны и могут отсутствовать, поэтому
разные работы попадают в одну ячейку, и связи всех них накапливаются на одной.

**Становится:** отображение по `ELEMENT_ID` — идентичности, которая в файле
уникальна по определению. Имя остаётся содержимым работы, но перестаёт быть ключом.

Уникальность имён, которую требует Р4, — свойство **входного документа**, а не
файла Ramus. Опираться на неё при чтении файла нельзя; проверять её — задача
прохода обнаружения непереносимого.

**Дополнительно.** После смены ключа один и тот же поток всё ещё может прийти в
одну работу несколькими секторами (ветвление). В списке ICOM он называется один
раз: повтор снимается при добавлении, с сохранением порядка первого появления.

## Перечень проверочных моделей

Новая сущность в тестах: список файлов `.rsf`, по которому идут табличные проверки
разбора, round-trip и декомпиляции.

| Поле | Смысл |
|---|---|
| `Path` | путь к файлу |
| `Name` | имя для сообщений теста |
| `ExpectRefusal` | ожидается ли отказ по непереносимому содержимому |

`ExpectRefusal` нужен потому, что модели ведут себя по-разному по делу, а не по
недоработке: `ИзготовлениеЮбки.rsf` декомпилируется целиком, `testModel.rsf`
обязан получить отказ из-за безымянных работ. Тест, требующий одинакового исхода
от обеих, был бы неверен.

## Виды диагностики

Структура `diag.Code` не меняется. Добавляется только способ узнать полный список
во время выполнения теста: объявления читаются из `internal/diag/code.go`
синтаксическим анализатором.

Список кодов остаётся закрытым и упорядоченным по файлу объявлений; порядок
объявления и есть порядок в отчёте мета-теста, чтобы диагностика непокрытых видов
читалась рядом с исходником.
