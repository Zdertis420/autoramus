# Phase 1. Проверка результата

Все команды — из `ramusc/`, если не указано иное. Каждый сценарий проверяет
требование спецификации.

## Подготовка

```bash
cd ramusc
go build -o ramusc ./cmd/ramusc
```

Проверочные модели — те же три: `../examples/ИзготовлениеЮбки.rsf`,
`../examples/ФормированиеТП.rsf`, `testdata/testModel.rsf`.

## Сценарий 1. Перечень потерь собирается сопоставлением

```bash
go test ./internal/rsf -run Loss -v
```

Ожидается: на каждой модели перечень получен вычитанием перенесённого из описи
атрибутов, а не из зашитого списка видов. Эталоны потерь зафиксированы.

Проверка самой проверки — добавить в проверочные данные атрибут, которого раньше
не было, и убедиться, что он попал в перечень **без правки кода**. Это и есть
отличие чёрного списка от белого.

Требования: FR-001, FR-002, FR-006. Критерий: SC-002.

## Сценарий 2. Служебное в перечень не попадает

```bash
go test ./internal/rsf -run 'Loss|Inventory' -v
```

Ожидается: атрибутов метамодели (`AttributeId`, `AttributeName`, `QualifierId`,
`QualifierAttributes`, `F_BASE_FUNCTION_QUALIFIER_ID`) в перечне нет.

Отдельно проверяется, что правило не отсекает лишнего: `F_SECTORS` и `F_STREAMS`
помечены системными, но их содержимое — данные автора, и оно обязано учитываться.
Это опровергнутая гипотеза Р-2, и регрессия сюда вероятна.

Требования: FR-004.

## Сценарий 3. Частичное чтение считается потерей

```bash
go test ./internal/rsf -run PartialRead -v
```

Ожидается: из записи о модели читаются две колонки из девяти, и потеря заявлена
по остальным семи (`DEFINITION`, `MODEL_LETTER`, `PROJECT_NAME`,
`TERM_ATTRIBUTE`, `USED_AT`, `CHANGE_DATE`, `CREATE_DATE`), а не отсутствует
вовсе.

Требования: FR-003.

## Сценарий 4. Непонятое доезжает через люк

```bash
./ramusc decompile ../examples/ФормированиеТП.rsf -o /tmp/f.yaml
grep -A3 'raw:' /tmp/f.yaml | head -20
./ramusc validate /tmp/f.yaml; echo "код: $?"
```

Ожидается: у работ видны записи люка с цветами, шрифтом и статусом; у сегментов
стрелок — свойства подписи; у модели — непрочитанные колонки. Проверка языка
даёт код 0.

Требования: FR-007, FR-009, FR-011. Критерии: SC-004, SC-005.

## Сценарий 5. Люк не подменяет собой поля языка

```bash
go test ./internal/decompile -run RawIsLastResort -v
```

Ожидается: атрибута, для которого у языка есть своё поле (имя работы, иерархия,
геометрия), в люке нет. Люк — крайнее средство, а не свалка.

Требования: FR-008.

## Сценарий 6. Значение люка переживает обратное чтение

```bash
go test ./internal/decompile -run RawRoundTrip -v
```

Ожидается: документ напечатан и прочитан обратно; имена и значения атрибутов
совпадают с исходными, включая многоколоночные.

Требования: FR-010. Критерий: SC-005.

## Сценарий 7. Потерь на трёх моделях не остаётся

```bash
for f in ../examples/ИзготовлениеЮбки.rsf ../examples/ФормированиеТП.rsf; do
  ./ramusc decompile "$f" >/dev/null
done
```

Ожидается: пусто в потоке ошибок — после расширения люка терять нечего.

Правило предупреждения проверяется отдельно, на собранных вручную данных: настоящей
модели с незакрываемой потерей нет.

```bash
go test ./cmd/ramusc -run LossWarning -v
```

Ожидается: вывод печатается полностью, перечень идёт в поток ошибок и в шапку
YAML, код возврата 0.

Требования: FR-017, FR-018, FR-019. Критерий: SC-003a.

## Сценарий 8. Ссылочная колонка помнит цель

```bash
go test ./internal/decompile -run ColumnTarget -v
```

Ожидается: у колонки типа `ref` и `list` указан целевой справочник; у колонки
`text` поля цели нет; вывод проходит проверку языка, и цель распознаётся как
существующий справочник.

Проверяется на собранных вручную данных: ссылочных колонок нет ни в одной модели.

Требования: FR-012, FR-013. Критерий: SC-006.

## Сценарий 9. Приёмка целиком

```bash
make check
```

Ожидается: зелёно.

```bash
git diff --stat ramusc/testdata/golden/
```

Ожидается: изменены эталоны декомпиляции трёх моделей — в них появились секции
люка. Это осознанное изменение. Всё остальное — не изменено; в частности, эталоны
диагностики валидатора и вывод `dump` не двигаются.

Требования: FR-014, FR-015. Критерий: SC-008.

## Что этими сценариями не проверяется

- Обратная сборка `.rsf` из люка: генератора нет. Форма значения задумана
  достаточной, но подтвердить это можно только на генераторе.
- Элементы DFD: сняты с объёма решением по фиче `001`.
- Люк у потока, классификатора и колонки: класть туда на сегодняшних моделях
  нечего, проверяется только тем, что он допустим и не печатается пустым.
