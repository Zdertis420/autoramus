# auto-ramus

Компилятор моделей [Ramus](https://github.com/Vitaliy-Yakovchuk/ramus):
текстовое описание модели → файл `.rsf`, минуя GUI.

```bash
ramusc model.yaml -o model.rsf
```

`ramusc` берёт описание модели на YAML или JSON, проверяет его,
сам раскладывает блоки и стрелки и записывает файл, который Ramus открывает как
свой.

Побочная, но не последняя цель — звено пайплайна «LLM → валидатор → компилятор»:
нейросети выдают текст заметно охотнее, чем координаты прямоугольников.

---

## Пример

`skirt.yaml` — целиком, без сокращений. Ни одной координаты в нём нет:
геометрию раздаёт раскладка.

```yaml
model: Изготовление юбки
author: Ножкин А.М.
page: A4

flows: [Ткань, Фурнитура, Правила изготовления, Швея-закройщица,
        Выкройка, Раскройное оборудование, Швейная машинка,
        Швейно-вышивальная машинка, Детали изделия, Собранное изделие, Юбка]

functions:
  - name: Изготовление юбки
    in:        [Ткань, Фурнитура]
    control:   [Правила изготовления]
    mechanism: [Швея-закройщица, Раскройное оборудование, Выкройка,
                Швейная машинка, Швейно-вышивальная машинка]
    out:       [Юбка]

  - name: Раскрой материала
    of: Изготовление юбки
    in:        [Ткань]
    control:   [Правила изготовления]
    mechanism: [Швея-закройщица, Раскройное оборудование, Выкройка]
    out:       [Детали изделия]
    note: Ручной раскрой по лекалам

  - name: Сшивание деталей
    of: Изготовление юбки
    in:        [Детали изделия]
    control:   [Правила изготовления]
    mechanism: [Швея-закройщица, Швейная машинка]
    out:       [Собранное изделие]

  - name: Добавление фурнитуры
    of: Изготовление юбки
    in:        [Собранное изделие, Фурнитура]
    control:   [Правила изготовления]
    mechanism: [Швея-закройщица, Швейно-вышивальная машинка]
    out:       [Юбка]
```

Иерархия задаётся ссылкой `of`, а не вложенностью. Связи выводятся по совпадению
имён потоков: `Детали изделия` в `out` у раскроя и в `in` у сшивания — это одна
стрелка, рисовать её отдельно не нужно.

```bash
ramusc examples/skirt.yaml -o skirt.rsf   # 4 работы, 11 потоков, 28 секторов
```

Больше примеров — в `examples/`: `skirt.json` (тот же документ в JSON),
`skirt-full.yaml` (все секции языка: классификаторы, DFD, ручная раскладка,
люк `raw`).

## Состояние

Работает и проверено тестами:

| | |
|---|---|
| Разбор JSON и YAML | позиции `line`/`column` у каждого узла, строгость к незнакомым полям |
| Валидация | 57 видов диагностики: схема, иерархия, баланс ICOM, классификаторы, раскладка |
| Раскладка | порядок блоков, координаты, маршруты стрелок, граничное ветвление деревом |
| Генерация `.rsf` | модель, работы, потоки, секторы — файл открывается в Ramus |
| Декомпиляция | `.rsf` → канонический YAML/JSON; служит исполняемой спецификацией генератора |

Не сделано:

| | |
|---|---|
| Каналы | у каждой стрелки свой номер ординаты, и две стрелки на одной координате сливаются на рисунке. **Следующая работа** |
| `ramusc render` | превью раскладки в SVG; каталог пуст |
| Классификаторы и `raw` в `.rsf` | языком описаны, валидатором проверяются, декомпилятором читаются — но генератор их пока не пишет |
| Ветвление от производителя | поток от одной работы к нескольким потребителям идёт отдельной линией к каждому. Рисунка для этого случая нет ни в одной модели набора, и писать геометрию без меры не стали |
| `ramus-gui` | пустые каталоги, работа не начиналась |

## Сборка

Нужен Go 1.26+. Зависимостей ровно три: `santhosh-tekuri/jsonschema/v6`,
`gopkg.in/yaml.v3`, `golang.org/x/text`.

```bash
cd ramusc
make build          # ./ramusc
make check          # форматирование, go vet, тесты
make cross          # dist/ для linux, windows, darwin (amd64 и arm64)
```

Бинарь никуда не устанавливается: кто хочет — добавляет в `PATH` сам.

## Команды

```
ramusc <файл>                   компиляция; по умолчанию model.json -> model.rsf
ramusc <файл> -o out.rsf        явный вывод; -o - для stdout
ramusc validate <файл>          проверка, человекочитаемый вывод
ramusc validate <файл> --json   проверка, машинный вывод
ramusc dump <файл.rsf>          показать модель из готового файла Ramus
ramusc decompile <файл.rsf>     напечатать её на входном языке (YAML; --json)
ramusc version | help
```

Компиляция начинается с той же валидации: при ошибке выдаёт те же объекты и
поддерживает тот же `--json`. Двух наборов сообщений об одном и том же не бывает.

**Коды возврата:** `0` — успех, `1` — вход невалиден, `2` — внутренняя ошибка
или неверный вызов. Паника ловится и превращается в код `2` со стеком: вызывающая
сторона не должна получить пустой вывод и код падения.

**Формат `--json`** — массив объектов:

```json
{
  "severity": "error",
  "code": "unknown_flow",
  "message": "поток «Выкройки» не объявлен в flows, похоже на «Выкройка»",
  "path": "/functions/1/mechanism/2",
  "line": 24,
  "column": 18
}
```

`line`/`column` обязательны и тянутся с самого разбора: без них редактор не
поставит маркер на полях. Коды — закрытый список (`internal/diag/code.go`),
они только добавляются и не переименовываются задним числом.

## Как устроено

```
парсер → IR → валидатор → раскладка → генератор .rsf
```

Этапы идут лесенкой: следующий запускается, только если предыдущий не нашёл
ошибок. Сыпать десяток наведённых сообщений поверх синтаксической ошибки
бессмысленно, а смысловые проверки за счёт этого вправе считать форму документа
верной.

| Пакет | Что делает |
|---|---|
| `internal/syntax` | фронтенды JSON и YAML, общее дерево с позициями |
| `internal/schema` | `model.schema.json` через `go:embed` — единственный источник истины по форме документа |
| `internal/ir` | внутреннее представление и его сборка из дерева разбора |
| `internal/diag` | диагностика, сортировка, вывод текстом и JSON |
| `internal/validate` | схема и смысл: иерархия, баланс, классификаторы, раскладка, подсказки по близким именам |
| `internal/layout` | IR без геометрии → IR с геометрией |
| `internal/generate` | IR → `.rsf` поверх заготовки внутри бинаря |
| `internal/rsf` | ZIP, таблицы, разбор модели IDEF0, правило туннелирования, обратная запись |
| `internal/decompile` | `.rsf` → IR → канонический YAML/JSON |

Пакеты не знают друг о друге больше необходимого. Раскладка ничего не знает про
ZIP и XML, генератор — только про IR. За счёт этого фронтенд можно заменить,
не трогая работу с ординатами и кросспоинтами, и наоборот.

**Раскладка** — единственная нетривиальная часть. Формулы не придуманы, а сняты
с моделей, которые Ramus разложил сам: диагональ от `(80, 80)` до `(660, 322)`,
блок `72 × 50.4`, вертикаль прямой связи ровно посередине промежутка между
блоками. Универсальные графовые раскладки (force-directed, Sugiyama целиком)
сознательно не используются: они дают корректный, но не-IDEF0-шный рисунок.

меня» — сверка с настоящими файлами.

## Разработка

**Детерминированный вывод.** Одинаковый вход даёт побайтово одинаковый выход:
временные метки в ZIP фиксированы, порядок обхода не зависит от отображений,
сборка идёт с `-trimpath`. Иначе две сборки одной модели дают разные байты, и
тесты приходится писать через распаковку вместо сравнения хеша.

**Эталонные тесты.** Поведение фиксируется файлами, а не утверждениями в коде.
Битая модель кладётся в `ramusc/testdata/models/` (их 39), ожидаемая диагностика —
в `ramusc/testdata/golden/`. Валидные документы лежат отдельно, в
`ramusc/testdata/documents/`. Эталоны переписываются осознанно:

```bash
make golden
```

Диффом эталона видно ровно то, что изменилось в сообщениях, — ради этого они и
лежат файлами.

**Проверочные модели** — их четыре, перечень в `ramusc/internal/fixtures`; каждая добавленная
вскрывала дефект, которого не показывали прежние. Новый файл добавляется в
перечень, код табличных тестов при этом не трогается.

**Каждый вид диагностики проверен.** `internal/diag/coverage_test.go` читает
список видов разбором `code.go` и требует, чтобы каждый возникал хотя бы на одной
модели. Новый вид без модели роняет сборку.

Перед коммитом — `make check`. Неотформатированный код считается ошибкой сборки,
а не замечанием на ревью.
