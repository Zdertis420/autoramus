# Tasks: Связи доезжают до `.rsf` — стрелки в файле

**Input**: Design documents from `/specs/006-arrow-links/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/

**Tests**: обязательны. Не по требованию спецификации, а по конституции: принцип
V («эталонные тесты и сверка с реальными файлами») и правило `make check` перед
коммитом. Числа маршрутов сверяются с `examples/тест.rsf` — моделью, которую
Ramus разложил сам.

**Organization**: задачи сгруппированы по историям спецификации; каждая история
проверяема отдельно.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: можно делать параллельно (разные файлы, нет зависимости от незакрытых задач)
- **[Story]**: к какой истории относится (US1…US4)
- Путь к файлу — в самой задаче

## Path Conventions

Всё живёт в `ramusc/` (модуль `github.com/Zdertis420/autoramus/ramusc`).
Тесты лежат рядом с кодом пакета, битые модели — в `ramusc/testdata/models/`
(там их битость и проверяется), валидные документы-фикстуры — в
`ramusc/testdata/documents/`, эталоны — в `ramusc/testdata/golden/`, настоящие
файлы Ramus — в `examples/`.

## Implementation Strategy

### MVP (Phase 1 + Phase 2 + US1)

1. Setup: проверочный документ с обратной связью, поправка спецификации.
2. Foundational: последовательности, вывод стрелок, крепления, номера.
3. US1: потоки и секторы в файле, предупреждение убрано.
4. **Остановиться и проверить**: `ramusc examples/skirt.yaml`, `dump`,
   `decompile`, и — обязательно — открыть файл в Ramus. Здесь секторов ещё
   немного, и если состав строк неверен, это видно сразу.

### Инкремент

1. MVP → файл со стрелками, пусть и по простым маршрутам.
2. + US2 → маршруты, совпадающие с тем, что рисует сам Ramus.
3. + US3 → согласованные уровни, сшивка кросспоинтов.
4. + US4 → ручная поправка.
5. + Polish → документы и эталоны.

Каждая ступень оставляет проект в рабочем состоянии: `make check` обязан
проходить на любой из них.

## Notes

- Порядок обхода всюду — порядок документа. Обход отображений ломает
  детерминированность, и это не стилистика, а принцип III конституции.
- Числа маршрутов не сочиняются: если меры нет, так и пишется в комментарии —
  как уже сделано для обратной связи (В9).
- Комментарий объясняет «почему»: почему середина, почему `-1` в `POINT_TYPE`,
  почему кросспоинт общий. Пересказ соседней строки не нужен.
- Новых кодов диагностики не заводится. Если покажется, что нужен, — сначала
  вопрос, не должен ли об этом говорить валидатор, который уже есть.
- Коммит после каждой задачи или логической группы; `make check` перед каждым.
